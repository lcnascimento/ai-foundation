# i18n

next-intl **without locale routing**: the locale comes from a cookie, not the URL. Don't add `[locale]` segments or locale middleware.

## Locale

- `i18n/request.ts` reads the locale cookie, validates it with an `isValidLocale` guard over the `locales` tuple from the `i18n` package, and falls back to `defaultLocale`. No `as Locale`.
- Changing locale writes the cookie through `shared/cookies/` and calls `router.refresh()` inside `startTransition` (see [data](data.md)).

## Messages

- Two layers, both loaded per locale with dynamic `import()` and merged in `i18n/request.ts`:
  - global namespaces (`common`, `errors`, `validation`) in the `i18n` package;
  - app namespaces (`nav`, `workspace`, one per feature area) in `apps/<app>/shared/_messages/<locale>.json`.
- A key added to one locale file is added to every locale file in the same change.
- Keys are camelCase (`apiKeys`, `trackingPlan`). Namespaces mirror the feature, not the component.
- Every user-facing string goes through messages: pages, error boundaries, placeholders, aria-labels, toasts. `global-error.tsx` renders outside `NextIntlClientProvider`, so it loads messages for the cookie locale itself.
- A missing key is a bug to fix in the message files, not a `try/catch` with a fallback string.

## Using translations

- Server components without async APIs call `useTranslations("ns")`; async server components call `await getTranslations("ns")`; client components call `useTranslations`.
- Design-system components and business primitives in `ui` never translate: the caller passes translated strings as props (see [components](components.md)).
- Format numbers, currency and dates with next-intl's formatters (`useFormatter`/`getFormatter`) or the `utils` formatters, never with hand-built strings.
